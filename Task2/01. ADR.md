# ADR флагманской инициативы

## ADR-001. Приоритизация подозрительных операций

### Контекст

RetailBank обрабатывает 20–25 миллионов операций в месяц. Правила и внешние сигналы отмечают около 35 тысяч, а финмониторинг способен проверить около 10 тысяч. Средний разбор занимает 12 минут. Историческая выборка смещена: проверялись преимущественно операции, уже выбранные существующими правилами. Формально подтверждённых схем — единицы.

### Жёсткие ограничения
- данные операций относятся к банковской тайне
- допустимость передачи данных во внешний контур определяют комплаенс/DPO/юристы
- ИИ не заменяет установленные правовые процедуры (AML)
- финальное решение остаётся за банком
- нельзя обучаться только на ранее эскалированных случаях и считать их точно подтверждённым мошенничеством

### Рассмотренные варианты постановки
| Вариант | Решение |
| --- | --- |
| Классификатор схема / не схема | Отложено, недостаточно подтверждённых меток |
| Обучение только на эскалациях | Отклонено, воспроизводит смещение существующих правил |
| Только правила | Остаются baseline |
| Ранжирование операций для проверки | Выбрано для пилота |

### Решение по данным
Создать программу экспертной разметки. Разметка поступает одновременно из:
- разобранной приоритетной очереди
- постоянной вероятностной контрольной выборки

Эскалации, правила и результаты расследований используются как слабые сигналы, но не как эквивалент подтверждённой схемы. 

### Решение по размещению
**Пилот:** внутренний контролируемый контур RetailBank.

**Продакшен:** предварительно on-prem либо self-hosting в облачном контуре банка.

Public API с реальными операциями не рассматривается до подтверждения допустимости такого потока комплаенсом/DPO/юристами.

### Решение по модели
На этапе пилота - модель ранжирования/поиска аномалий, а не классификатор 'схема / не схема'.

Окончательная модель выбирается по результатам приёмочного прогона на собственной репрезентативной выборке.

### Допущения
- банк может организовать регулярную экспертную разметку
- признаки доступны в момент формирования очереди
- возможно сформировать вероятностную контрольную выборку из общего потока
- инфраструктура выбранного внутреннего контура способна обеспечить необходимую обработку

### Основные риски
- смещение исторической выборки
- недостаток подтверждённых положительных случаев
- новая модель может создать собственное смещение отбора
- рост ручной очереди
- использование чувствительных данных
- зависимость (vendor lock-in) при переходе к внешнему провайдеру

#### План выхода от вендора
Интеграцию модели выполнять через собственный адаптер и не связывать бизнес-процесс с API конкретного поставщика. При смене кандидата повторяется приёмочный и регрессионный прогон. 

### Триггеры пересмотра

ADR пересматривается, если:
- накоплено достаточно качественной разметки для классификации
- меняется законодательство или заключение комплаенса/DPO
- изменяется профиль нагрузки
- модель не превосходит текущий baseline
- ручная очередь превышает допустимую ёмкость
- меняются цена, SLA или версия модели
- появляется кандидат, лучше выполняющий выходной контракт

### Статус
**Предварительно принято**

На текущем этапе рекомендуется пилотировать сервис приоритизации ручной проверки, одновременно создавая программу получения несмещённой экспертной разметки. Переход к классификатору 'схема / не схема' возможен только после накопления достаточного источника правильного ответа.
