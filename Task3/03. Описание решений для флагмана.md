## Ответственность компонентов

| Шаг процесса | Модель / код / человек | Причина | Цена ошибки |
| --- | --- | --- | --- |
| Получение и проверка признаков | Код | Структура и доступность проверяются детерминированно | Некорректный вход модели |
| Оценка приоритета | Модель | Нужна обучаемая закономерность | Неверный порядок очереди |
| Калибровка и порог | Код | Зафиксированная логика рабочей точки | Лишняя/пропущенная эскалация |
| Пороговые правила | Код | Уже известная детерминированная логика                 | Потеря обязательного сигнала |
| Валидация/fallback | Код | Модель не должна сама решать, допустим ли её результат | Некорректный результат попадёт в очередь |
| Проверка операции | Человек | Финальное решение остаётся за банком | Ошибочное действие в отношении клиента |


## Режим обработки

#### Асинхронная обработка через очередь

Для операции не требуется синхронный ответ клиенту, результат нужен для формирования очереди сотрудников. Асинхронный режим позволяет сглаживать пики и повторять обработку при временной недоступности модели.

Повторная обработка одной версии операции не должна создавать дубликат задания в очереди. Журнал фиксирует версию модели, вход, результат и решение человека.

## Выходной контракт

| Поле | Источник | Способ проверки | Что при нарушении |
| --- | --- | --- | --- |
| `operation_id` | Банковская система | Обязательное, операция существует | Не передавать результат модели |
| `priority_score` | Модель + калибровка | Диапазон допустимых значений | Fallback |
| `priority` | Детерминированный код | Допустимая категория | Fallback |
| `model_version` | Model Service | Обязательное | Fallback |
| `rule_signals` | Rule Engine | Проверка структуры | Передать человеку с отметкой |
| `fallback_reason` | Validator | Значение из справочника причин | Ошибка контракта |
| `evaluated_at` | Сервис | Обязательная дата/время | Не использовать результат |

Отсутствующие обязательные признаки не заполняются догадкой. Операция переводится на fallback. Результат модели валидируется до изменения позиции в рабочей очереди.

## Уровень автоматизации

Модель только рекомендует приоритет. Автоматически выполняются:
- получение и проверка признаков
- расчёт score
- применение правил
- сортировка очереди после валидации

Человек:
- анализирует операцию
- принимает решение по результатам проверки
- фиксирует результат

Прямого пути 'модель → действие в отношении клиента' нет. Это соответствует принципу HITL: человек остаётся встроенным в процесс принятия решения.

## Fallback

Операция передаётся на резервный путь/ручную обработку, если:
- отсутствуют обязательные признаки
- признаки устарели
- значения выходят за область, представленную в обучающих данных
- клиент или сегмент не имеет достаточной истории
- score находится в зоне воздержания около порога
- результат модели расходится с сигналом детерминированного правила
- модель недоступна
- Feature Service недоступен
- нарушена схема выходного контракта
- превышены лимиты сервиса

При недоступности ML сервис продолжает использовать существующие пороговые правила — текущий baseline.

## Мониторинг

| Уровень | Что отслеживаем | Триггер реакции |
| --- | --- | --- |
| Вход | Пропуски, устаревание признаков, изменение распределений, новые сегменты | Рост относительно baseline → анализ данных |
| Модель | Распределение score, доля fallback, качество по накопленной разметке | Значимое отклонение от пилотного уровня → повторная проверка |
| Очередь | Размер, возраст операций, доля обработанных, нагрузка сотрудников | Рост очереди сверх пропускной способности → ограничение/отключение ML-приоритизации |
| Человек | Доля исправлений/несогласий с приоритетом | Рост → анализ модели и сегментов |
| Бизнес | Результативность первых N проверок относительно baseline | Нет улучшения → откат к текущей приоритизации |

## Границы доверия и безопасность

Для флагмана нет клиентского текста/документа, поэтому граница недоверенного контента в контексте LLM не требуется. Важны границы между банковскими источниками, ML-контуром и результатом вероятностной модели.

На диаграмме компонентов обозначены такие границы:
- TB-1 - банковские данные и внешние сигналы входят в AI-контур
- TB-2 - результат модели передаётся детерминированной части системы

| Граница | Угроза | Что делаем |
| --- | --- | --- |
| TB-1 | Утечка банковской тайны за допустимый контур | Обработка только в согласованном контуре, минимизация передаваемых признаков, сервисные доступы по минимальным полномочиям |
| TB-1 | Некорректные/подменённые входные данные | Проверка схемы, источника, свежести и допустимых диапазонов |
| TB-2 | Ошибочный или некорректный ответ модели используется системой как доверенный | Отдельный валидатор контракта, модель не вызывает бизнес-действия напрямую |
| TB-2 | Подмена модели/весов или зависимостей | Фиксировать версию и происхождение модели и зависимостей, контролируемое обновление |
| TB-2 | Компрометация сервисного доступа модели | Минимальные права, модели не предоставляются права на действия в банковских системах |
